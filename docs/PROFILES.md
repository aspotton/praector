# Runtime profiles and prompt design

[Documentation index](README.md) | [Agent protocol](AGENT_PROTOCOL.md) | [Architecture](ARCHITECTURE.md)

Praector uses role-based runtime profiles rather than mythology/persona names. Every profile inherits a mandatory global engineering contract from `internal/assets/prompts/global.md`, has a mandatory role-specific operating contract under `internal/assets/prompts/`, and receives the durable Task Envelope generated by `internal/praector/envelope.go`.

You can inspect the installed contracts directly:

```bash
praector profile list
praector profile show coordinator
praector profile show critic
praector profile show plan_review
praector profile show advise
```

`praector profile show <profile>` prints the inherited global engineering contract first and the selected role-specific contract second.

The built-in prompt files are:

```text
internal/assets/prompts/global.md
internal/assets/prompts/coordinator.md
internal/assets/prompts/critic.md
internal/assets/prompts/plan_review.md
internal/assets/prompts/research.md
internal/assets/prompts/implement.md
internal/assets/prompts/review.md
internal/assets/prompts/advise.md
```

The global contract and role contracts are intentionally separate. The Envelope carries durable task/context/delegation mechanics and injects the global contract into every fresh attempt; the profile prompt supplies the specialized reasoning stance. This means delegated, retried, and resumed work inherits the same engineering rules without copying generic prose into each task objective.

## Global engineering contract

The global contract applies to all profiles and establishes repository-wide execution discipline:

- after substantive repository writes, inspect relevant `README.md` and `AGENTS.md` files and update them when durable knowledge would otherwise be lost;
- prefer the smallest coherent code change that satisfies the objective;
- consider callers/callees, variables/shared state, control flow, configuration, tests, and other surrounding assumptions when changing code;
- inspect parent/child/sibling/consumer relationships for inheritance, interfaces, protocols, composition, or related classes;
- surface worthwhile adjacent work as recommendations/risks/questions rather than silently expanding scope;
- favor simple direct changes over unnecessary abstraction;
- match surrounding style and avoid sweeping syntax/formatting churn;
- use docstrings or the repository's equivalent documentation convention when they add durable understanding;
- preserve these rules when creating plans or durable tasks for another worker.

Role prompts reinforce these rules rather than duplicating them. The coordinator translates them into task-specific contracts; the critic and plan reviewer look for missing impact/scope analysis; the implementation worker performs the impact/documentation checks; and the implementation reviewer verifies adherence without failing for merely optional deferred improvements.

## Role map

| Praector profile | Purpose | Capability | Rough OMO analogue |
| --- | --- | --- | --- |
| `coordinator` | decision-complete planning plus durable graph authority | read-only, graph-authority | Prometheus planner plus part of Atlas orchestration |
| `critic` | pre-plan gap analysis, hidden intent, scope/QA hazards | read-only | Metis / plan-consultant |
| `plan_review` | practical executability review of the proposed task graph | read-only | Momus / plan-reviewer |
| `advise` | deep technical/architecture recommendation | read-only | Oracle / architect consult lane |
| `research` | bounded evidence gathering | read-only | Explore + Librarian responsibilities combined in the current release |
| `implement` | bounded code/file execution and self-verification | write | Sisyphus-Junior / implementation worker concept |
| `review` | independent verification of integrated implementation | read-only | post-implementation QA/gate reviewer, not Momus |

The mapping is conceptual, not a dependency. Praector does not import or invoke Oh My OpenAgent.

## Why `review` and `plan_review` are different

This distinction matters:

- `plan_review` asks whether the proposed graph is executable before write work runs.
- `review` asks whether completed integrated implementation actually satisfies its objective.

A plan can be executable and still produce a buggy implementation; both gates solve different failure modes.

## Coordinator / planner

The coordinator owns the work graph, not product implementation. Its prompt requires it to:

- classify the dominant work intent before decomposing;
- inspect project evidence before assuming;
- use the smallest safe graph rather than delegating ceremonially;
- request `critic` for materially ambiguous/high-risk work;
- request `advise` for architecture/tradeoff decisions that materially affect the design;
- make non-trivial write tasks depend on a `plan_review` gate when useful;
- make task objectives decision-complete with DELIVERABLE / SCOPE / MUST HAVE / MUST NOT / VERIFY context;
- submit its result and exit instead of waiting for workers.

Clearly trivial documentation-only work may remain low-ceremony. Non-trivial implementation work has a deterministic `plan_review` floor; critic/advice/research remain conditional on risk, ambiguity, architecture, or evidence needs.

Unlike an interactive planning agent, Praector does not let managed workers ask the operator live questions. If evidence, critic, and advice still leave a requirement-defining ambiguity with no safe reversible default, the coordinator should block/fail planning with the exact unresolved choice rather than inventing an answer. A future durable operator-input gate can add interview-style clarification without making session continuity part of correctness.

## Critic

The critic is deliberately pre-planning. It does not judge code quality or implement solutions. It classifies the request and looks for the few issues that would change the plan:

- hidden requirements or contradictions;
- requirement-defining ambiguity;
- scope inflation / adjacent cleanup / premature abstraction;
- missing compatibility, migration, rollback, or integration constraints;
- architecture decisions lacking real constraints;
- research without exit criteria;
- vague or human-only acceptance/QA.

It returns actionable planner directives and clearly separates observed facts, assumptions, and unresolved choices.

For required-critic collections, the initial critic is a preflight, not a permanent approval. Praector seals it to the first critic-informed material plan at final plan-review handoff. Later changes to implementation/research/advice contracts or their meaningful dependencies require a revalidation critic. A fresh coordinator consumes that revalidation; if incorporation changes the material plan again, another critic round is required before plan review.

## Plan reviewer

The plan reviewer is approval-biased and blocker-focused. It asks whether a capable worker can execute the current graph without getting stuck. It checks:

- references and assumptions are grounded;
- each task has a usable starting point and bounded deliverable;
- dependencies are coherent and non-contradictory;
- verification is executable;
- scope boundaries prevent obvious overreach;
- executing the graph exactly as written can satisfy all Collection MUST/MUST NOT and acceptance requirements without knowingly relying on a later repair for a defect already visible in the plan.

It does not reject for style or because it prefers another architecture. A known acceptance violation is a true blocker; Praector has no implicit fault-injection exception. A failed verdict stays blocking and causes Praector to wake a coordinator for graph repair; after that coordinator completes, the same durable plan-review Task runs again in a fresh Attempt. A non-failed nonterminal final plan-review gate is single-flight: later coordinators reuse that gate rather than creating a parallel final-review generation.

## Strategic advisor

The advisor is the deep judgment lane. Its prompt emphasizes:

- pragmatic minimalism;
- reuse of existing patterns/components;
- one primary recommendation rather than an indecisive option dump;
- explicit tradeoffs and material uncertainty;
- concrete evidence;
- a trigger for when the recommendation should be revisited.

It also signals confidence and coarse implementation investment when those factors affect the decision, and identifies the condition that would justify revisiting the recommendation. It advises; it does not implement.

## Researcher

The researcher answers one bounded evidence question and distinguishes observed fact from inference. It prefers reproducible source/test/config evidence and stops when the question is answered rather than broadening indefinitely.

## Implementation worker

The implementation worker treats its Task and completed dependencies as the contract. It should make the smallest coherent change, inspect the meaningful surrounding impact surface, avoid adjacent scope growth, match local code style, inspect relevant README/AGENTS files after writes, run relevant verification, and never claim a command passed when it was not executed. Completed implementation results should also include a concise reviewer-facing `pr_summary` and 3–8 concrete `changes` bullets; these are durable delivery metadata used directly by `praector collection pr`, while verification commands remain in `evidence`.

## Implementation reviewer

The implementation reviewer re-reads the integrated candidate rather than trusting the implementer result. It independently inspects the diff and meaningful impact surface, reruns appropriate tests, verifies relevant durable documentation when applicable, reproduces important behavior when practical, and submits `verdict: pass|fail` with evidence. It records optional adjacent improvements as non-blocking recommendations/risks rather than failing for preference.

## Prompt composition

At runtime the model receives:

```text
common ORCH TASK ENVELOPE
+ mandatory internal/assets/prompts/global.md engineering contract
+ profile purpose / OWN / ASK / DELEGATE boundary
+ mandatory internal/assets/prompts/<profile>.md operating contract
+ durable context JSON
```

For coordinator, critic, and plan-review profiles, the durable context also includes a snapshot of the current Collection graph so planning roles can reason about the actual task/edge state rather than reconstructing it from prose.

Dependency summaries preserve role-relevant fields such as verdict, recommendation, confidence, planner directives, QA directives, assumptions, evidence, risks, and unresolved items.

## Model-specific prompting

Praector currently keeps one role contract per profile rather than maintaining separate Claude/GPT prompt bodies. This is intentional for now: the durable orchestration contract should remain stable across local models. Model-per-profile selection is configurable in `.praector/project.toml`.

A future prompt-calibration layer may add model-family framing without changing the role semantics or authority boundaries.


## Stateful correctness cross-check

For work involving shared mutable state, the `critic` must identify concurrency, atomicity, synchronization, and process-boundary hazards. `plan_review` must challenge those independently rather than merely confirm that critic directives were copied into an implementation task.


## Review severity invariant

The implementation `review` profile must fail when observed behavior violates an explicit objective, MUST HAVE, acceptance criterion, security/data-integrity invariant, or stated numeric limit. Merely documenting the limitation does not waive the requirement. For shared mutable state, review independently checks thread/task/process concurrency and atomicity rather than assuming a single process serializes requests.

### Coordinator / plan-review handoff

The coordinator defines implementation contracts first and then requests `plan_review` as its final blocking planning handoff. Creating that review atomically gates existing implementation tasks. If the review passes, Praector finalizes the waiting coordinator automatically; the coordinator does not receive another ordinary attempt. If the review fails, explicit coordinator-repair work is created and the reviewer remains blocking until the repaired graph passes.
