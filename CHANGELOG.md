# Changelog

All notable changes to Praector are recorded here. README and focused documentation are intentionally release-version-neutral.

**Repository rule:** every repository change must update this file. Add work under `Unreleased` while it is in progress; when publishing a release, move those entries into the new version section and keep the newest release first.

## Unreleased

- Hardened **Git workspace identity** so the branch Praector integrates is provably the branch Praector assigned. Previously a worker was free to move HEAD or invent a branch and nothing compared the merged state against the durable assignment. **Read-only profiles** now capture a `WorkspaceSnapshot` (HEAD, attached branch, `git status --porcelain=v1 --untracked-files=all`, and the worktree's HEAD reflog) before the attempt and validate all four afterward. The reflog comparison catches a checkout-away-and-back that leaves HEAD, branch attachment, and status looking unchanged again at completion, and the violation detail is carried into the `READ_ONLY_CAPABILITY_RETRY` event. Read-only restoration now uses `checkout --detach --force` plus `clean -fd` instead of `reset --hard`, so recovering a candidate can never move or destroy a branch a worker happened to attach to. **Implementation tasks** must remain attached to their assigned branch at `PrepareTask`, `Checkpoint`, and `IntegrateTask`, while read-only task worktrees must be detached HEAD. Before any merge, `IntegrateTask` proves the worktree HEAD and `refs/heads/<branch>` both name the durable checkpoint, refuses a dirty integration target, merges the **immutable checkpoint SHA** rather than the mutable branch name, and verifies the checkpoint is reachable from the resulting target HEAD, so a stale or switched-to branch can no longer integrate "successfully". A checkpoint or integration validation failure now submits a failed result and records `IMPLEMENTATION_WORKSPACE_VIOLATION` instead of aborting the attempt with a bare error. **Prompts** make the ownership contract explicit: `implement` gains a Praector-owned Git workspace section that overrides free-form objective wording about branch names, `coordinator` must translate generic "work on a separate branch" instructions into the Task-branch -> Collection-branch workflow, `plan_review` treats worker branch-lifecycle instructions as a blocker, `review` judges only the assigned detached HEAD using non-mutating commands such as `git show`, and the shared read-only capability discipline adds detached-HEAD/history preservation. Mirrored in the Python reference implementation, with regression coverage for branch escape failing closed before integration, integration by immutable validated checkpoint, and read-only detection of a checkout away and back.

- Extended the repo-local `$praector` skill to operate Praector through the **local binary as well as the MCP server**. The skill now selects a surface explicitly (advertised `praector_*` tools, else `command -v praector`/`praector --version`, else an honest unavailability statement), states that both adapters call the same typed `Service`/`Store` paths, and keeps every durable rule surface-neutral. A new `references/cli.md` maps each command to its MCP equivalent and records where the CLI is genuinely stronger rather than merely differently named: attached `praector run` executes inline and blocks (with `--detach` as the enqueue-only equivalent, and the one-scheduler-owner rule for `task retry`/`collection revise` resumption), CLI context resolution via explicit ID → `PRAECTOR_PROJECT_ID` → nearest `.praector/project.toml` instead of MCP's explicit-id-only rule, real `collection pr`/`accept`/`cleanup`/`init` side effects with no privileged opt-in gate (so authorization plus a `--dry-run`/`--stat` preview is the check), streamed `logs --tail` versus MCP log metadata, and read-back verification via `status`/`graph`/`task show`/`collection show`. Documentation that previously implied MCP-only operation was corrected across `SKILL.md`, its `workflows.md` boundary/delivery guidance, the skill's `agents/openai.yaml` interface text, README, and AGENTS; no runtime, schema, or CLI behavior changed.

- Added a repo-local `$praector` agent skill under `.agents/skills/praector/` for operating the live Praector control plane through MCP. The progressively disclosed package teaches the durable Project/Collection/Task/Attempt/Session model, profile and planning/review boundaries, Git/Dolt/worktree/recovery semantics, safe create/monitor/retry/revise/delivery/acceptance/cleanup workflows, and the complete current MCP tool/resource schema. Its metadata declares the local Streamable HTTP MCP dependency, supports both explicit `$praector` invocation and implicit routing for live Praector work, and distinguishes plan-only MCP PR/acceptance operations from real privileged init/cleanup effects.

- Completed a final MCP protocol, security, daemon-context, and external-conformance hardening pass on the daemon/MCP surface. **Protocol/version honesty:** the server now advertises only the single MCP revision it actually implements (`2025-06-18`) and **refuses** any other requested `initialize` revision with a JSON-RPC Invalid-params error carrying the honest supported set, instead of echoing an unsupported version it does not implement. Every post-`initialize` Streamable-HTTP request must carry an `MCP-Protocol-Version` header equal to that revision (a missing or unsupported header is a plain HTTP 400; Praector does not assume the pre-2025-06-18 revision it does not implement). **DNS-rebinding hardening:** before reading, decoding, or dispatching any tool/resource, the transport validates the request Host/local-authority and Origin — a foreign authority or Origin (or a port mismatch) is rejected with HTTP 403; this is defense in depth layered on top of the unchanged authoritative loopback socket-bind gate. **No daemon-cwd:** MCP operations no longer fall back to the daemon process working directory — a tool whose domain op would otherwise resolve a project implicitly must be given an explicit `PRJ-*` project identifier or a resolvable `COL-*`/`T-*` id (`praector_run` now requires `project`; `status`, `graph`, `doctor`, `task list`, `project show`, `memory add/list`, and `decision add` enforce the same rule), while CLI cwd convenience is byte-identical. **Absolute init:** `praector_init` requires an absolute `root_path` and refuses `.`, `..`, relative names, and empty. **Accurate semantics and content types:** `collection pr`/`accept` remain plan-only, `collection cleanup` and `praector_init` are described as performing real removal/registration, JSON-backed resources advertise `application/json` while CLI/help-text resources advertise `text/plain`. **External conformance:** an independent black-box oracle (`scripts/mcp_conformance.py`, driven in CI by `TestMCPExternalConformanceOracle` against a live loopback listener) verifies negotiation, the header/Origin contracts, `tools/list`, `resources/list`/`read`, a safe read call, and a safe durable queue-write, independent of the in-process Go protocol tests. All prior MCP invariants are preserved: disabled by default, `[mcp] enabled`/`PRAECTOR_MCP` solely gates the listener with privileged exposure independent of it, loopback-only with empty-host/wildcard refused (`IsLoopbackAddr` untouched), no scheduler/process launch from the MCP bridge, queue writes through the shared `Service`/`Store` paths, `pr`/`accept`/`cleanup` default-off and non-finalizing, no `PRACTOR_*` alias, the `commandHelp`→`serviceOps`→`mcpSurface` 1:1 parity tests still enforced, and no new runtime dependency (static `CGO_ENABLED=0` builds unchanged).

- Hardened and clarified the daemon/MCP surface (acceptance revision). MCP listener enablement and privileged-write exposure are now **completely independent**: `[mcp] enabled` / `PRAECTOR_MCP` is the sole gate that starts the loopback listener, and `[mcp] privileged` / `PRAECTOR_MCP_PRIVILEGED` only controls whether privileged tools are exposed on an already-enabled listener — setting privileged no longer implicitly enables the listener (`config.go` `LoadMCPServerConfig`). MCP `praector_init` is now a **privileged, explicit-root** operation: it requires a `root_path`, registers that requested target repository (never the daemon process working directory), and is refused while the privileged opt-in is off; the CLI `praector init` keeps its cwd-based behavior unchanged. Added regression coverage for the full enable/privileged matrix over both the file and env paths, the canonical-only `PRAECTOR_*` env surface (the misspelled `PRACTOR_MCP_PRIVILEGED` is confirmed inert — no alias), MCP init target-scoping and privileged-refusal, and the extended privileged tool set. Tightened parity terminology across README, AGENTS, architecture/operations/development docs, and code comments to accurate **command/surface coverage parity** rather than unrestricted behavioral parity, since `collection pr`/`accept` (and now `init`) return validation results/plans or privileged registration and never themselves push, merge, or finalize acceptance. All existing MCP invariants are preserved: disabled by default, loopback-only with empty-host/wildcard addresses refused, no scheduler/process launch from MCP, queue writes via the same Service/Store paths, `pr`/`accept`/`cleanup` still default-off and plan-only, and the `commandHelp`→`serviceOps`→`mcpSurface` 1:1 parity tests remain enforced. No new dependencies and no change to CLI behavior.
- Extended the MCP surface to **command/surface coverage parity** driven off the canonical `commandHelp`/`serviceOps` registry so the CLI and MCP surfaces cannot drift in coverage ("now and always"). Every leaf command becomes one callable MCP tool (read-only queries and parameterized actions) and every command namespace plus the launch-only `daemon` command becomes one readable resource. Read-only parity is always on; pass-through queue-write tools (`task request`, `result submit`, `memory add`, `decision add`, `task add-dependency`/`supersede`, `coordinator attention`, `run`, `task retry`, `collection revise`) reuse the identical gated `Store` methods so policy, planning, audit, cycle, and revision checks are never bypassed. Privileged write tools — explicit-root `init`/registration plus the collection-finalizing `collection pr`, `collection accept`, and `collection cleanup` — are **default-off** behind a separate, independent `privileged` opt-in (`[mcp] privileged` / `PRAECTOR_MCP_PRIVILEGED`): when disabled they are neither advertised nor callable, and even when enabled `pr`/`accept` only run the durable acceptance/PR validation and return the resulting plan without pushing, merging, or implicitly accepting, so direct acceptance and external PR delivery remain operator-side actions. A commandHelp-driven parity test asserts 1:1 CLI↔MCP coverage in both directions, plus tests for the privileged opt-in's default-off behavior and an end-to-end proof that an MCP queue-write call yields the same durable effect + audit event as the shared Service op the CLI delegates to. No new external dependencies and no change to orchestration semantics or CLI behavior.
- Added an opt-in, **loopback-only** MCP server to the native runtime. When enabled, `praector daemon` hosts a dependency-light, stdlib JSON-RPC 2.0 / MCP-core streamable-HTTP listener (`internal/praector/mcp`) as a background goroutine **decoupled from the reconcile loop and `scheduler.lock`**, so AI agents can drive Praector over the same durable control plane the CLI uses. The listener runs concurrently with the daemon but performs only Store reads and durable **enqueue-only** actions through the shared typed `Service` seam (`internal/praector/mcp_server.go`), mirroring the CLI `--detach` path: "execute"-style tools create durable Collections/Tasks via the same `CreateCollectionWithCoordinator`/`CreateTask` paths and rely on the running daemon to execute them. It never constructs a scheduler, launches worker processes, runs a collection inline, or bypasses policy/review/acceptance (enforced by a source-level test). It is **disabled by default**, binds `127.0.0.1` only (a non-loopback address is refused at startup), and defers authentication/identity to the future remote-access boundary. Enable via `~/.praector/config.toml` `[mcp]` `enabled`/`addr` (parsed by the same dependency-light parser used for project markers) or a `PRAECTOR_MCP` environment override. No new external dependencies and no change to orchestration semantics or CLI behavior.
- Extracted a shared typed service layer (`internal/praector/service.go`) as the single domain seam that both the CLI and the future MCP adapter call, so the two surfaces can never diverge ("now and always"). Every `cmd*` function now delegates its durable domain work to one typed `Op(ctx, Input) -> Output` per CLI command while keeping argument parsing, stdout formatting, exit codes, and scheduler/process launching adapter-side; CLI output, formatting, and exit codes are unchanged. A `serviceOps` registry maps each `commandHelp` entry 1:1 to an op, enforced by a new parity test, so adding a CLI command without wiring a domain op fails the build. The layer launches no processes and introduces no second store or orchestration implementation.

## 0.2.5

- Fixed the 0.2.4 active-generation reconciliation gap exposed by MCP dogfooding. A RUNNING Collection now retains its latest initial/revision coordinator as the generation anchor even after that coordinator has completed, allowing the stronger engine contract to supersede an obsolete legacy critic after handoff. When the original generation coordinator is already COMPLETE, Praector creates a fresh `Apply inherited research revalidation` coordinator so corrected critic findings can reconcile the current material task contracts before a new final plan review. Historical COMPLETE Collections remain untouched.
- Made authoritative research constraints transitive across the hard dependency DAG. Task Envelopes, consumer-result validation, and implementation/review work now inherit completed research ancestors even when the direct dependency is only a critic, plan review, or implementation task. This prevents canonical protocol/security directives from disappearing at the plan-review -> implementation -> review boundaries.
- Added claim-time fail-closed enforcement as an independent safety layer. A plan review cannot start if the latest required critic is invalid under the current inherited-research contract; an implementation cannot start unless the latest plan review has `verdict=pass` and both that plan review and the latest critic validate against their completed transitive research ancestry. Scheduler reconciliation is therefore no longer the sole barrier protecting write work.
- Added global/implementation contract precedence for machine-projected `inherited_research_constraints`: canonical research directives override conflicting free-form task objectives, dependency summaries, critic/coordinator paraphrases, or prior plan text unless a durable explicit-exception decision authorizes departure. Added regressions for the exact MCP failure where a task objective said absent initialize params should succeed while authoritative research required missing `protocolVersion` to return Invalid Params.

## 0.2.4

- Promoted structured research directives into first-class inherited planning constraints. Task Envelopes now expose compact `inherited_research_constraints` directly from completed research claims, including task-qualified claim id, normative level, source/authority, and the canonical planner directive. Coordinator, critic, plan-review, and implementation-review contracts explicitly treat those directives as authoritative unless a durable exception decision says otherwise.
- Strengthened `research_consistency` from claim-id acknowledgement to per-claim disposition. Every research-consuming critic/plan-review/review must map each claim to `preserved`, `strengthened`, or `explicit_exception`, repeat the exact inherited directive, list any derived directives, and cite a durable Collection decision for an explicit exception. Passing consistency may not report contradictions, and changed/dropped inherited directives are rejected before becoming durable planning evidence.
- Added active-generation upgrade revalidation for the stronger contract. If an in-progress initial/revision coordinator depends on a completed pre-0.2.4 critic that only used the older `checked_claim_ids` trace, Praector preserves that critic as historical evidence, creates a fresh critic against the same explore/research inputs, supersedes the old critic, rewires the active coordinator, and emits `RESEARCH_CONSISTENCY_REVALIDATION_REQUIRED`. Historical completed Collections are not retroactively reopened.
- Added native/reference regressions for the exact MCP dogfood failure: research says missing/non-string/malformed `protocolVersion` must be Invalid Params while a downstream critic paraphrase tries to allow absent params. The new contract rejects the changed inherited directive and forces active-generation revalidation instead of accepting `research_consistency.verdict=pass` at face value.

## 0.2.3

- Fixed managed OpenCode launches for large evidence-rich prompts. Praector now streams the complete Task prompt over child stdin instead of placing it in the process argument vector, preventing Linux/macOS/Windows exec argument-size failures such as `fork/exec ...: argument list too long` without truncating exploration, research, critic, or plan-review evidence. Managed stdin is closed deterministically after the prompt is written so OpenCode headless runs receive EOF instead of hanging on inherited open stdin. Harness logs record `prompt_transport=stdin`; prompt byte count and SHA-256 provenance remain unchanged.
- Preserved the 0.2.2 upgrade-compatibility fix for historical 0.2.1 critic fingerprints while retaining research-aware fingerprints for new work.

## 0.2.2

- Preserved upgrade compatibility for completed 0.2.1 Collections after 0.2.2 added completed research-result digests to material-plan fingerprints. Existing valid 0.2.1 critic seals are recognized through the historical fingerprint contract, so upgrading cannot retroactively turn a COMPLETE reviewed Collection into BLOCKED or prevent `collection revise`; all new 0.2.2 planning continues to use the stronger research-aware fingerprint, and genuinely changed plans still require critic revalidation.
- Added deterministic fresh-external-evidence planning policy. Objectives involving evolving external protocols/standards, provider integrations, regulation/compliance, explicit freshness, or changing dependency/vendor contracts can now require `research` before material planning. For those generations, `explore` and fresh `research` run independently, `critic` depends on both, and the coordinator remains blocked until the evidence-informed preflight completes. Purely local implementation work keeps the lighter `explore -> critic` path.
- Strengthened the `research` contract with machine-checkable provenance: `as_of`, source ids/authority/references, material claims with normative level and claim-to-directive effect, confidence, and classified verification oracles. Research results that omit required provenance, cite unknown sources, use unsupported normative/directive/oracle classes, or claim an exception without a durable decision id are rejected before becoming planning evidence.
- Added claim-level research traceability and consumer consistency enforcement. Structured research now requires stable claim ids plus source authority levels; free-form planner directives must be backed by structured claims, while critic, plan-review, and research-aware review results must report `research_consistency` covering every claim they consumed. A normative evidence claim cannot be silently reversed or weakened without an explicit durable exception decision that actually exists in the Collection. Claim-id collisions across multiple research tasks are task-qualified before consumer validation so evidence traces remain unambiguous.
- Strengthened external-conformance acceptance. A passing review for protocol/provider work must record an actually used `independent_implementation`, `official_reference_oracle`, or `live_provider_oracle`; an implementation-owned/out-of-process black-box client remains `black_box_test` and is insufficient by itself unless a durable exception decision explicitly records why no authoritative oracle is practical.
- Added evidence-aware planning staleness. Completed research result digests now participate in the material-plan fingerprint, so materially refreshed external evidence can invalidate an older critic/plan seal rather than leaving stale planning silently accepted. Critic and plan-review prompts now explicitly compare local exploration to fresh external requirements, challenge evidence-to-directive contradictions, and distinguish implementation-owned black-box tests from authoritative reference/live-provider oracles.
- Added structured `RESEARCH_REQUIRED` escalation for critic, plan-review, review, and advise tasks. A read-only specialist can submit a bounded externally-verifiable question with `status: waiting`; Praector creates blocking research and automatically makes the same durable task eligible for a fresh attempt after that evidence completes instead of forcing the agent to guess.
- Added deterministic security/threat-model and external-conformance policy flags. Network/auth/privilege trust-boundary work receives explicit threat-model challenges, while external protocol/provider implementation requires an independently classified verification oracle when practical.
- Added project capability metadata for current external research. Existing/legacy projects default to research-capable; projects can set `[capabilities] current_external_research = false`. If deterministic planning or a specialist escalation requires fresh retrieval while that capability is unavailable, Praector blocks/quarantines the Collection with `RESEARCH_CAPABILITY_REQUIRED` rather than allowing model-memory substitution.
- Added task input-lineage evidence and reconciliation review. Praector records the material-plan fingerprint plus direct prerequisite lineage when a task attempt starts. If an implementation finishes after its accepted planning/research/prerequisite lineage changed, its mandatory independent review becomes an explicit reconciliation review against the current accepted state and records `RECONCILIATION_REQUIRED`; completed downstream work is preserved rather than blindly discarded or silently accepted.
- Expanded Task Envelope result summaries so structured research provenance (`as_of`, `sources`, `claims`, `verification_oracles`) and bounded `research_required` requests survive delegation into critic, coordinator, plan-review, and review contexts.

## 0.1.39

- Strengthened semantic review repair lineage. A successful review with `verdict=fail` now completes as durable historical evidence instead of waiting on its own repair. The repair implementation depends on that failed review, and successful repair integration creates a **fresh durable review Task/context** rather than resuming the original reviewer. The fresh review independently re-evaluates the repaired candidate and carries verification lineage for both the repair implementation and the original implementation it corrected.
- Updated terminal/acceptance semantics for the stronger lineage model: historical completed `verdict=fail` reviews are preserved and no longer permanently poison acceptance; every completed review must still have an explicit `pass|fail` verdict, and every completed implementation must be covered by a later independent `verdict=pass`. Added native/reference regressions for fresh post-repair review creation and repaired lineage acceptance.
- Shifted known acceptance failures left into planning. Coordinator, critic, and plan-review contracts now forbid intentionally dispatching implementation work that knowingly violates Collection MUST/MUST NOT, security, or acceptance requirements on the theory that downstream review will repair it. Plan review must fail such a graph. Praector still has no durable fault-injection/human/exec exception authorization, so intentional acceptance contradictions remain blocking operator issues until such a mechanism exists.

## 0.1.38

- Added a capability-specific workspace-hygiene contract to every read-only Task Envelope. Coordinators, critics, plan reviewers, researchers, reviewers, and advisers now baseline the starting Git status, prefer verification modes that avoid incidental repository writes, restore only cache/build/test artifacts caused by their own checks, and verify the final worktree matches the starting baseline before submitting results. The contract explicitly warns against discarding pre-existing or committed candidate state merely to make `git status` clean.
- Documented non-mutating verification as prevention rather than a replacement for runtime enforcement. `PYTHONDONTWRITEBYTECODE=1` is provided as an optional Python example when bytecode caches are irrelevant, while Praector's deterministic post-run dirty-worktree check, rollback, same-task retry, and retry-budget escalation remain unchanged. Added native/reference envelope regressions proving read-only profiles receive the hygiene contract while `implement` retains write capability.

## 0.1.37

- Reclassified read-only workspace mutation as an execution/protocol failure rather than a semantic review/plan failure. When a coordinator, critic, plan reviewer, researcher, reviewer, or adviser mutates its read-only worktree, Praector rolls the changes back, records the concrete attempt as failed, and retries the same durable Task while retry budget remains. This prevents a reviewer capability violation from incorrectly spawning coordinator repair work for an implementation that was never actually rejected.
- Added durable `READ_ONLY_CAPABILITY_RETRY` events and native/reference regressions proving the same task returns to `READY` before graph-level escalation; only retry-budget exhaustion produces a terminal failed task that can trigger coordinator attention. Real `verdict=fail` review behavior is unchanged and still creates blocking implementation repair.

The guard covers atomic task creation, direct dependency-edge insertion, and single-flight plan-review reuse.
- Removed fake `T-*` dependency placeholders from the runtime Task Envelope and documented that agents must use exact task IDs returned by Praector. Coordinator examples now rely on Praector's automatic final-plan-review gating rather than fabricating a future plan-review ID.
- Added native and reference regressions proving missing/cross-Collection dependencies are rejected before mutation while preserving existing DAG-cycle enforcement.

## 0.1.31

- Added first-class GitHub pull-request delivery with `praector collection pr`. A reviewed `COMPLETE` Collection can now push its integration branch, create a GitHub PR through the authenticated `gh` CLI, or reuse an existing PR for the same collection branch without duplication. PR delivery is idempotent and durable: Praector records provider/number/URL/state/base/head/source commit separately from Collection execution/acceptance state, so reopening a Collection with `collection revise` and completing fresh reviewed work updates the same open PR on the next `collection pr`. The command supports `--draft`, `--title`, `--base`, `--remote`, `--dry-run`, and `--open`; PR copy is assembled deterministically from durable implementation/review results rather than generated by a new model task. ## 0.1.30

- Closed the revalidation handoff loop exposed by `COL-f575af95a4`. Planning policy no longer treats `WAITING` coordinators as active graph-shaping prerequisites of a final `plan_review`; a waiting coordinator has already handed control to a blocking child/review and therefore must never be wired back ahead of that same review generation. Coordinator-requested final plan review is now single-flight at the store/API layer: if a non-failed nonterminal `plan_review` already exists, Praector reuses it, atomically attaches new critic/research prerequisites, blocks the coordinator on that gate, and gates current implementations instead of creating another review generation. If that review currently waits on the same active coordinator, the final handoff atomically flips `coordinator -> plan_review` into `plan_review -> coordinator` rather than ever persisting both directions. Explicit caller-as-review-prerequisite requests are ignored because the blocking handoff creates the valid opposite edge. This prevents repeated critic-revalidation rounds from manufacturing parallel final-review gates or reverse-edge quarantines.

## 0.1.29

- Added legacy dependency-cycle migration and daemon isolation. Before reconciliation, Praector now scans upgraded collections for the two pre-write cycle edges older releases could persist (`implement -> plan_review` and `coordinator -> plan_review` when part of a cycle) and removes only those protocol-invalid edges, recording `LEGACY_DEPENDENCY_CYCLE_REPAIRED`. Unknown historical cycle shapes are not guessed at: the affected collection is marked `BLOCKED`, a durable `DEPENDENCY_CYCLE_QUARANTINED` event is recorded, its runnable tasks are skipped, and the global daemon continues processing other collections. This closes the upgrade failure where one old collection could terminate `praector daemon` as soon as the 0.1.28 DAG guard encountered it.

## 0.1.28

- Made the durable `depends_on` graph acyclic by invariant rather than by prompt convention. Every new hard dependency is checked for transitive reachability before commit, including the initial dependency/blocking/gating batch published with a new task. Scheduler reconciliation repairs legacy coordinator↔plan-review transitive cycles, collapses multiple unstarted final plan-review gates to the newest surviving gate, rewires waiting coordinators and implementations onto it, and finalizes every waiting coordinator released by a passing final review rather than waking stale planners. The exact multi-node Twilio recovery topology that exposed the 0.1.27 gap is now a regression test.

## 0.1.22

- Added deterministic critic revalidation for materially changed plans. The initial required critic is sealed to the first critic-informed material plan at final plan-review handoff. After that, changes to implementation/research/advice contracts or their meaningful dependencies stale the critic. Praector blocks plan review and implementation at claim time, runs a fresh critic against the changed graph, and requires a fresh coordinator to consume those findings. If that coordinator materially changes the plan again, another critic round is required. Status/timestamp churn and orchestration-only edges do not invalidate the critic.
